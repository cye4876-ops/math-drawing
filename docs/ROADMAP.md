# 总路线图

## 一、为什么是 9 版

版本划分**不按功能数量**切，而按**架构断点**切——即"哪些需求会逼我们推翻已有代码"。全功能盘过一遍后，真正引发重构的断点只有 4 个：

1. 从"一条曲线"到"多条曲线 + 参数联动"
2. 从"纯数值"到"需要符号形式"
3. 从"纯 2D 平面"到"3D + 可插拔文档层"
4. 从"绘图器"到"可编程笔记本"

其余功能（统计、复变、数论、向量场）都能**零重构**挂进已有结构。所以版数由这些断点决定，再加 UX 收尾与打包分发，落在 8–10 之间，取 **9**。

```
                        └────────────────> v0.6 导出与分享 <──┘
                                              │
                    ┌─────────────────────────┼──────────────────────┐
                    v                        v                      v
              v0.7 统计               v0.8 3D 与场            v0.9 复变·数论·符号
                    └─────────────────────────┼──────────────────────┘
                                              v
                                     v1.0 Notebook 与教学
```

**关键依赖说明：**

- **v0.6 依赖 v0.5**：URL 状态编码与导出需要能序列化"图 + 曲线 + 视图"的完整文档状态。若 v0.5 未定型文档模型，v0.6 会返工。
- **v0.7 / v0.8 / v0.9 相互独立**，可调整顺序或并行。当前排序依据是"投入递增 + 重模块后接轻模块"。
- **v1.0 依赖全部**：Notebook 要把所有模块的渲染结果当作文档元素插进单元格。

## 四、三个必须先讲清楚的设计决策

### 决策 1：v0.5 是分水岭，不是普通一版

到图论阶段，画布上同时存在**连续曲线**与**离散节点/边**，两者的命中检测、缩放语义、撤销粒度完全不同。

**做法**：在 v0.5 把渲染层重构成**图形元素注册制**——每个元素自报"如何绘制"与"如何命中"。而不是继续堆 `if` 分支。

这是全套里**唯一一次真正的架构调整**。刻意排在中间而不是最后：越晚做，需要改造的既有代码越多。

### 决策 2：AST 与参数系统必须在 v0.2 落地

| 资产 | 若推迟会怎样 |
|---|---|
| **AST** | v0.6 的 TikZ 导出需要表达式的**符号结构**才能生成 LaTeX；只有"字符串求值"就得从零重写。v0.9 的符号计算同理 |
| **参数可序列化** | 参数滑块、动画录制、分享链接三件事全部依赖它。晚做等于三件事重做 |

### 决策 3：复杂度刻意错开

v0.5 图论、v0.8 3D、v0.9 符号计算是三个最重模块。排布上保证**每个重模块之后必接一个轻模块**，避免出现"连续很长时间什么都看不到"的低反馈期。

以 v0.3 为基准 6 单位：

```
v0.1 骨架   ███ 3

v0.3 绘图   ██████ 6   ← 基准
v0.4 交互   █████ 5
v0.5 图论   ██████ 6
v0.6 导出   ███ 3
v0.7 统计   ███ 3
v0.8 3D     █████ 5
v0.9 复变等 ████ 4
v1.0 收官   ████ 4   （含打包分发，常被低估）
```

**两个验收节点：**

- **节点 A：v0.4 结束**（约 18 单位，不到总量一半）—— 手上已有一个能日常使用的函数绘图器
- **节点 B：v0.5 结束** —— 函数绘图 + 图论两大核心诉求齐备

建议在这两处停下来实际用一段时间，再决定后续投入。

## 六、风险清单

| 风险 | 影响版本 | 说明与对策 |
|---|---|---|
| **自适应采样最难写对** | v0.3 | 隐函数尤甚。排期要留足；先用"病态函数基准集"定义对错 |
| **图论布局"手感"** | v0.5 | 力导向参数调不好会像果冻。需反复试参，预留调优时间 |
| **性能悬崖** | v0.3 起 | 元素过千后 SVG/DOM 会崩。**开局就定好 Canvas / DOM 分工**，事后重构代价极大 |
| **范围蔓延** | 全程 | 11 个模块全做不现实。严格按版本边界执行，新想法进 backlog 不插队 |
| **第三方扩展 API 不稳定** | 工具链 | 若使用依赖非公开 API 的 VS Code 扩展，升级后可能失效 |

## 七、每版的通用验收模板

每个版本规格文档都按以下结构编写，验收时逐项打勾：

```markdown
## 工作内容      <- 要做什么，分解到可执行条目
## 交付物        <- 产出的文件/功能/文档清单
## 验收标准
  ### 功能验收   <- 每条都能客观判定通过/不通过
  ### 质量验收   <- 性能阈值、错误处理、边界情况
  ### 文档验收   <- 该版必须同步写出哪些文档
## 明确不做      <- 本版刻意排除的内容，防止范围蔓延
## 风险与陷阱    <- 已知的坑
## 验收方式      <- 用哪些命令/测试/手工步骤验证
```

> 所有性能阈值均为**工程建议值**，验收时可根据实际情况调整；一旦调整，必须同步改文档并记录原因。
